ISHIZUE.

The foundation your AI stands on.

ISHIZUE, from the Japanese word ishizue, a foundation stone, is an AI harness: the layer that connects models, tools, memory and permissions and runs agents on top of them. Every part of it is a plugin, including the agent loop.

Router

Every request, to a model that suits it.

Conversations run through Auto, the local router. It reads the request, rules out what can’t do the job, ranks what can and records why. Auto answers with the models your organisation installs and approves, on its computers or its approved workstation.

Developer preview

  1. Admit only private models

    Model apps running on the same computer (Ollama, LM Studio, vLLM, SGLang and llama.cpp), plus one approved workstation on your private network over HTTPS. Public internet addresses are refused.

  2. Rule out what can’t do the job

    Models whose context window can’t hold the request, that can’t read an attached image, or that aren’t cleared for tool use are set aside before any scoring.

  3. Read the task

    A fixed reader for Japanese and English sorts the message into one of eight kinds (quick, chat, agentic, reasoning, code, maths, vision, long) and judges how hard it is. No model is called and no prompt tokens are spent.

  4. Rank once

    One decision scores every remaining model and thinking setting together: the smallest suitable model for a quick reply, the strongest with thinking on for hard work.

  5. Answer, or move once

    If the chosen model fails before it starts answering, Auto moves once to the next ready model. It never moves to a hosted model.

  6. Record why

    The choice and its reasons are written to the session log, and the chat shows which model answered.

Decision engine

Decisions you can audit.

Behind Auto is a decision engine with a simple promise: the same inputs give the same answer. It weighs each candidate on five factors, and holds back when the top two options are too close to call.

In testing: the combined ranking of models and thinking settings

The five factors and their weights

  • ×4

    Fit for the task

    Does this model and thinking setting suit this kind of task?

  • ×2

    Size fit

    The smallest model for a quick reply, the strongest for hard work.

  • ×2

    What you taught it

    Ratings, retries and changes to the thinking setting. Older lessons count half after 14 days. Kept on the same computer.

  • ×1

    Placement

    On this computer, or on your workstation.

  • ×−2

    Recent failure

    A model and thinking setting that failed the same sort of request (with tools, with images, or plain chat) in the last 15 minutes ranks lower; it is still used when nothing else fits.

  • The weights are deployment settings, so they can be tuned for each customer.
  • The engine is replaceable: another engine can take its place without changes to the router.
  • It runs on the computer’s own processor and makes no network call.

It is a transparent scoring rule, not a trained neural network. The combined ranking of models and thinking settings is still being tested for release, and trained or hardware-accelerated engines are planned.

Orchestrator

Big jobs, shared between agents.

There is no separate orchestration server to buy. Orchestration is built into the agent loop and the plugins around it.

Developer preview

  • Parallel tools

    Up to ten independent tool calls run at once in each step. Calls that depend on order run one at a time.

  • Helper agents

    Self-contained parts of a task go to helper agents with a fresh context, working in the background. You can message, interrupt and list them. By default up to eight continuable helpers run at once; one-shot helpers are counted separately.

  • Workflows, on request

    For a large job, and only when someone asks for one, the agent writes a sandboxed script that shares the work out to many helpers and returns one combined result.

  • Long goals

    A goal holds one long objective across turns and restarts, for up to 256 rounds. The assistant can mark a goal blocked only after the same obstacle has lasted at least three rounds in a row.

  • Plan first

    In plan mode ISHIZUE explores and writes a plan for you to approve. In the Standard, Code and Creator modes, plan mode refuses file writes and edits until you approve the plan; commands are not held, so set an access mode and approvals for firm limits.

  • Crash recovery

    A checkpoint is written before every model call and every action, so an interrupted session can resume. An interrupted action is reported as “outcome unknown”, never silently repeated. A checkpoint is for recovery, never an undo.

Multi-agent work with small local models is still being tested. There is no agent-team feature.

Agent work and file tools need a local model whose server supports tool calling, or your approved workstation; other models are used for chat.

Memory and RAG

Memory you can inspect.
Knowledge that names its source.

Three local stores come built into the default assistant, in the desktop app, the web interface and the command line. None of them makes a network call.

Developer preview

  • ISHIZUE Memory

    Facts and preferences someone asks it to keep, recalled in later chats.

  • Knowledge Brain

    Project knowledge. Every record names its source: a person, or a file in the project.

  • Graph RAG

    Links the team approves between records. A search finds keyword matches, then brings in every record one link away and shows the relation that connected it.

  • Saved only through visible actions, shown as cards in the chat. Ask, and any item is forgotten.
  • Kept as readable files in the user’s folder on that computer. On macOS and Linux they are owner-only (folders 0700, files 0600); on Windows, ISHIZUE sets no permissions of its own.
  • The same records always come back in the same order, with visible scores.

Search works by keywords and approved links today. Search by meaning, and knowledge graphs built automatically, are not built yet; we are exploring them.

Small models

Engineered for the models you can run.

A model on a laptop has a fraction of the memory of one in a data centre. ISHIZUE is built to spend that memory on the task.

  • Tools on demand

    Specialist tools load only when a task needs them. In one measured desktop chat, this started the conversation about 4,000 tokens lighter.

  • Compaction

    Long conversations are summarised automatically before the window fills, keeping the latest part word for word.

  • Big outputs, parked

    A tool result over 4,096 tokens is saved to a file, and the model gets the path instead of the flood.

  • Loop guards

    A model repeating itself is reminded at 3, 5 and 8 identical calls. The tenth is refused.

  • Models sized to the computer

    A shelf of 12 reviewed open models, each labelled Runs well, Slow or Won’t fit from the computer’s memory, graphics and free disk, with the arithmetic shown. Nothing downloads until someone presses Download.

ISHIZUE reads graphics memory only on Apple silicon and NVIDIA cards; other computers are judged by processor and memory.

Files

Works on real files, and shows what changed.

Developer preview
  • ISHIZUE reads, writes and edits the files in a workspace and runs commands there: Bash on macOS and Linux, PowerShell on Windows.
  • Word, Excel and PowerPoint files, PDFs, images, code and web pages open in a preview beside the chat. Previews of web pages and Markdown files may load images and other resources from the web.
  • The side panel also holds the workspace’s files and a terminal.
  • After a turn that changes files, a card lists each one with the lines added and removed, and every change opens in a split or unified review.
  • Creating and editing Word, Excel and PowerPoint files on the desktop is part of the developer preview; dedicated tools for these files are still in progress.

After a restart, earlier turns have no card. In a folder without version control, only edits made by ISHIZUE’s own file tools are listed.

Agent work and file tools need a local model whose server supports tool calling, or your approved workstation; other models are used for chat.

Automation

Reminders, schedules and long goals.

Developer preview

  • Automation tasks

    Automation tasks bring a reminder or a repeating job back into the chat that set it up: once, daily, on weekdays, weekly or on a custom rule. They run while ISHIZUE is open. If a task comes due while ISHIZUE is closed, it runs once when ISHIZUE opens again.

  • Goals

    A goal can be paused, resumed, edited or cleared from the goal bar above the message box.

  • Plan review

    A plan written in plan mode arrives as a card: approve it, or request changes and say what you want changed.

Control

You decide what the assistant may touch.

  • Read Only

    The assistant can look, but not change anything.

  • Workspace WriteDefault

    Where new chats start. ISHIZUE’s own tools keep changes inside the chosen folder, and ask before anything wider.

  • Full access

    No sandbox and no approval prompts. Choosing it from a menu asks for a risk confirmation first.

Approvals offer Allow once or Reject. They cover ISHIZUE’s own file and command tools only; plugin and MCP tools are not covered yet.

The command sandbox, by system

Commands the AI runs can change files only in the workspace and temporary folders, on macOS, Windows and Linux. On Windows, and on older Linux kernels without bubblewrap, this limit is partial. On every system the commands can still read files your account can read.

While web access is off, those commands cannot connect to the internet on macOS, or on Linux where bubblewrap can run. On Windows, on Linux without bubblewrap and in Full access, their network access is not restricted.

  • If no confinement method works, commands fail closed: they do not run at all rather than run unconfined.
  • On macOS and Linux, a command can still ask a local service that has its own network access, such as Docker or the system name resolver, to reach the network for it.
  • On Ubuntu 24.04, the default AppArmor setting can stop bubblewrap. ISHIZUE then falls back to Landlock, which does not restrict the network.
  • The same limits apply to the Python code the AI runs in the desktop app. Full access removes them.
  • Plugins and MCP servers run outside the sandbox. The browser’s rules, such as asking before it submits, sends, buys or deletes, are instructions to the model, not checks in code.

Sandboxing and approvals reduce risk; they are not a guarantee. ISHIZUE has not yet had an independent security audit.

Record

A record a security reviewer can read.

Developer preview

  • Trajectory

    Beside every chat: each model request, tool call and result, by turn and step, with timing, token use, the system prompt, the tool definitions and the diffs.

  • Session log

    Each session is written to a session log on the computer. Everything that reaches a model can be rebuilt from it.

  • Export

    A chat can be exported with its helper sessions and attachments as one ZIP file.

  • Route records and feedback

    Every routing choice is written to the session log with its reasons, and so are ratings and notes.

Access keys pasted into a message are hidden in sent messages, titles, previews and the goal bar, but not in the Trajectory tab, in model replies or in the session log.

Checkpoints are for crash recovery only, never an undo.

Where it runs

Your computers, your workstation, your servers.

  • This computer

    Five model apps (Ollama, LM Studio, vLLM, SGLang and llama.cpp) are found on the computer’s own local ports, with no setup. ISHIZUE never scans the network.

  • A workstation

    One approved workstation on the private network, over HTTPS, paired by a code from a helper program on the workstation.

  • Behind a gateway

    A gateway in front of the organisation’s own model servers, paired as Auto’s workstation; the gateway then chooses among its models.

Also included: the web interface, which accepts connections only from the same computer (127.0.0.1), and the command line.

Tailoring

One core.
An edition for each customer.

A customer edition is a layer of configuration on the same ISHIZUE everyone runs. It is delivered as settings and plugins, not as a fork.

Modes
Five come with ISHIZUE today: Chat, Standard, Code, Minimal and Creator. An edition adds its own, each with the tools, instructions and skills a role needs, listed under Your modes.
Skills
Procedures as skill files, loaded when a task needs them. Edits take effect without reinstalling.
Project rules
Standing instructions in project instruction files, read at the start of work.
Access
The deployment’s default access mode and approval rules.
Models
On the organisation’s computers, on its workstation or behind its gateway, with Auto’s weights tuned to the work.
Connections
The organisation’s own systems, through MCP servers the edition adds.

New capabilities still need plugin engineering, and there is no central admin lock yet: each person can change their own settings.

Before you decide

  • ISHIZUE is a developer preview, and changes that break compatibility are expected.
  • It has not yet had an independent security audit, and we publish no benchmarks.
  • Larger models need more memory. Fit labels are arithmetic, not speed tests.
  • On Windows, the command sandbox limits file changes only partly and does not restrict the network.
