03 · What it stands on

What your product stands on.

Your product brings its tools and the know-how of its field. ISHIZUE brings the rest: it reads each request, picks a model on the organisation’s own hardware, shares out the work, calls your tools, remembers what it is asked to and keeps the record.

Developer preview

Built from plugins, down to the agent loop.

Every part of ISHIZUE is a plugin: the model adapter, the tool registry, the session log, even the agent loop. Any part can be swapped through configuration, without patching ISHIZUE’s own code.

A partner product joins the same way, as an ISHIZUE plugin or as an MCP server running as its own program. Once the organisation’s edition includes it, its tools appear next to ISHIZUE’s own.

On the Plugins page, someone with access to the app turns whole plugins or single components on and off, and sees whether each one is running.

Plugins and MCP servers run outside the command sandbox, and approvals do not cover their tools yet.

How a product joins
In testing: the combined ranking of models and thinking settings

Eight kinds of task. One decision for each request.

Auto, the router, reads each new message on the computer, in Japanese or English, and decides what kind of task it is: quick, chat, agentic, reasoning, code, maths, vision or long.

Its decision engine then ranks every model and thinking setting it may use, in one decision. Equal inputs give the same answer, the engine holds back when the top two options are too close to call, and the choice is written to the session log with its reasons.

It is a fixed, weighted scoring rule, not a trained model. It learns from ratings, retries and changes to the thinking setting, and keeps what it learns on that computer.

How Auto decides
Developer preview

Helper agents, long goals and work on a schedule.

The main agent runs up to ten independent tool calls at once. It hands self-contained parts of a task to helper agents that work in the background: by default up to eight continuable helpers at once; one-shot helpers are counted separately.

A goal holds one long objective across turns and restarts, for up to 256 rounds. The assistant can mark a goal blocked only after the same obstacle has lasted at least three rounds in a row.

In plan mode ISHIZUE explores and writes a plan for you to approve. In the Standard, Code and Creator modes, plan mode refuses file writes and edits until you approve the plan; commands are not held, so set an access mode and approvals for firm limits.

Automation tasks bring a reminder or a repeating job back into the chat that set it up: once, daily, on weekdays, weekly or on a custom rule. They run while ISHIZUE is open. If a task comes due while ISHIZUE is closed, it runs once when ISHIZUE opens again.

Agent work and file tools need a local model whose server supports tool calling, or your approved workstation; other models are used for chat.

Multi-agent work and long tasks with small local models are still being tested.

How the agents work
Developer preview

Works on real files, and shows what changed.

ISHIZUE reads, writes and edits the files in a workspace and runs commands there: Bash on macOS and Linux, PowerShell on Windows.

Word, Excel and PowerPoint files, PDFs, images, code and web pages open in a preview beside the chat.

After a turn that changes files, a card lists each one with the lines added and removed, and every change opens in a split or unified review.

Creating and editing Word, Excel and PowerPoint files on the desktop is part of the developer preview; dedicated tools for these files are still in progress.

After a restart, earlier turns have no card. In a folder without version control, only edits made by ISHIZUE’s own file tools are listed.

Agent work and file tools need a local model whose server supports tool calling, or your approved workstation; other models are used for chat.

Files and documents
Developer preview

Memory and RAG, kept as files you can read.

ISHIZUE remembers facts and preferences when someone asks it to, and keeps them in that person’s profile on the computer.

Knowledge Brain records project knowledge with the source of every record.

Graph RAG links records only where the team asks for a link, and widens each search by one link, so related knowledge arrives together.

All three search by keyword on the computer, with no embedding service and no network call. Search by meaning, and graphs that build themselves, are not built yet; we are exploring them.

How memory works
Developer preview

Every step, on the record.

Beside every chat is its Trajectory: each model request, tool call and result, laid out by turn and step, with timing, token use, the system prompt, the tool definitions and the diffs.

Each session is written to a session log on the computer, and a chat can be exported with its helper sessions and attachments as one ZIP file.

When a customer’s security reviewer asks what the AI did and why, there is a record to show them.

Access keys pasted into a message are hidden in sent messages, titles, previews and the goal bar, but not in the Trajectory tab, in model replies or in the session log.

04 · Built for each customer

One maintained core.
An edition for every customer.

Because every part of ISHIZUE is a plugin, a customer’s edition is a layer of configuration on top of one core we maintain, not a separate copy that falls behind. We set it up around how that organisation works, and a partner’s product can be part of it.

Developer preview

  • Only the tools a role needs

    Each mode gives the assistant the tools, instructions and permissions its job needs: less to misuse, less to review.

  • More room for the work

    Small local models have small context windows, and tool descriptions travel with every request. Carrying fewer tools leaves more room for the task.

  • The organisation’s own way of working

    Procedures become skills that load when a task needs them, and standing rules live in project files.

  • Kept on the upgrade path

    The customer’s layer sits above ours, so an update replaces our layer and leaves theirs in place.

What we configure

  • Modes for each role
  • Skills from procedures
  • Project rules
  • Access modes and approvals
  • Models sized to the hardware
  • Auto’s decision weights
  • Memory and knowledge

Not yet: there is no central admin lock; each person can change their own settings.

05 · Local, precisely

Local-first, with the exceptions written down.

Local-first should be something a customer can check. This is what stays on their machines and what can go online, for the ISHIZUE desktop app as built from the developer preview, October 2026. It holds on macOS, Windows and Linux unless a line says otherwise.

Network use · ISHIZUE desktop app · developer preview · October 2026

Stays on the organisation’s hardware

  • Answers from Auto, from models on its own computers or one approved private workstation. There is no hosted model and no cloud fallback.
  • Routing decisions, made on the organisation’s own hardware without calling a model.
  • Memory, project knowledge and knowledge links, kept as files in the user’s folder.
  • Crash reports and logs, written to a folder on the computer and sent nowhere. Telemetry is off, and we run no collector.

Can go online

  • Web access and the browser, each off until someone turns it on. Search terms then go to a public search service.
  • Images in answers, and previews of web pages and Markdown files, which load images and other resources from the web.
  • Model downloads, when someone presses Download.
  • The voice model (in development), downloaded once, the first time voice input is used. Recordings go to a speech service only if someone enters its address.
  • A paired workstation, over HTTPS on the private network.
  • Commands the AI runs. While web access is off, they cannot connect to the internet on macOS (name lookups still work) or on Linux where bubblewrap can run, but they can ask a local service with its own network access, such as Docker, to reach it. On Windows, on Linux without bubblewrap and in Full access, their network access is not restricted.
  • Update checks, in builds packaged with an update address: signed Mac and Windows builds and every Linux build. The current Apple silicon build has none.
  • Spell-check dictionaries on Windows and Linux, which the desktop app may download; not yet checked on a build.
  • Plugin installs, MCP servers on the network, and the tools of plugins and MCP servers. Plugin tools that declare they use the internet follow the web-access switch, but the switch does not stop every plugin tool, and approvals do not cover these tools yet.

On-premises without us. ISHIZUE needs no Shristyverse cloud service, account or telemetry server.

We don’t call it air-gapped, because that has not been tested, and ISHIZUE has not yet been independently audited.

Where it runs

ISHIZUE is one desktop app, built from a single codebase for macOS, Windows and Linux, with a command line and a web interface that opens in a browser on the same computer. We offer it to client organisations for each of these systems on request, as a developer preview; no build has been through release testing yet.
